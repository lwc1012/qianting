# 从信息缺失到可用数据：为深潜救生艇均衡算法获取真实海水密度

**实验报告**

| 项目 | 内容 |
| --- | --- |
| 实验主题 | 从信息缺失到可用数据——识别项目真正需要但不存在的信息，并完成一次最小可行的数据获取 |
| 依托项目 | 深潜救生艇潜浮均衡智能计算系统（LBSS，Qt6/QML 桌面程序） |
| 实验日期 | 2026-10-14 |
| 数据获取周期 | 1 天（全流程离线可复现） |
| 产出物 | 276 条带质控标志与不确定度的海水密度记录 + 算法敏感性实验结论 |

---

## 摘要

本项目的均衡算法把海水密度写成了一个编译期常量 `1.020 kg/L`（`Main.qml:40`），而真实海水密度随海区、季节、深度变化，跨度可达 7.62 kg/m³（0.75%）。

本实验完成了一次**最小可行的数据获取**：从 NOAA WOA23（1991–2020 气候态）下载中国近海 4 个海区、4 个代表月份、0–300 m 共 29 个标准层的温度与盐度，用 EOS-80 状态方程复算原位密度，经 6 类质量控制后得到 **276 条可用记录**（464 条计划记录中 188 条因水深不足缺测）。

随后把真实密度逐条代入算法的**解析复刻**（复刻经 100% 命中率的解析判据校验），对 1500 个工况做敏感性分析，得到一个反直觉但可解释的结论：

> **密度常数错误影响的不是"大多数决策"，而是"少数临界决策"。** 逐条代入真实密度后决策改变的比例只有 **1.13%**，但其中排水分支一旦翻转，力矩损失会突变 **1687.7 kg·m**，相当于 **32 块压载铅**的调节能力；而不发生分支翻转时，最大力矩偏差仅 **17.6 kg·m**，**小于移动最小一块压载铅的台阶（53.2 kg·m）**。

因此本次实验改变的核心判断不是"要不要用真实密度"，而是**"该怎么用"**：不是简单替换常数，而是在少数临界工况上做保守化处理。

## 1 实验背景：缺失的是什么信息

### 1.1 项目当前对海水密度的使用方式

程序里海水密度是一个单一常量，被算法直接引用：

| 位置 | 代码 | 物理含义 |
| --- | --- | --- |
| `Main.qml:40` | `readonly property double waterDensity: 1.02` | 全程序唯一取值，单位 kg/L |
| `solve_departure()` `Main.qml:1157,1175,1178,1186,1189` | `missing * WATER_DENSITY * LIFEBOAT_TANK_LONG[group_id]` | 水舱未满时，把"少了多少升"折算成力矩损失 |
| `solve_rescue()` `Main.qml:1354` | `total_water_needed_L = total_water_needed_kg / WATER_DENSITY` | 由被救人员总重反算需要排出多少升压载水 |
| `solve_rescue()` `Main.qml:1380,1393,1406` | `discharge * WATER_DENSITY * LIFEBOAT_TANK_LONG[i]` | 各水舱排水带来的力矩损失 |
| `solve_rescue()` `Main.qml:1533` | 同上，写入决策日志 | 显示给操作员 |

### 1.2 缺失的信息不是"一个数"，而是四个维度

如果把需求写成一句话——"项目需要知道当前作业海域当前深度的真实海水密度"——那么对照现状可以拆出四类缺失：

| 缺失维度 | 现状 | 应有状态 | 影响 |
| --- | --- | --- | --- |
| **空间变化** | 一个数，不分海区 | 渤海/黄海/东海/南海各不相同 | 表层密度实测跨度 1020.30–1025.15 kg/m³ |
| **时间变化** | 一个数，不分季节 | 冬夏差别显著 | 黄海中部表层 1 月 1025.10 vs 7 月 1020.70 kg/m³ |
| **深度变化** | 一个数，不分深度 | 300 m 处比表层重约 5 kg/m³ | 南海北部 0 m 1022.93 → 300 m 1027.62 kg/m³ |
| **可信度信息** | 无数值不确定度、无来源 | 每条数据带不确定度与出处 | 无法判断"这个数有多可信" |

补充一条工程上的缺失：**密度值是被写死在源码里的**，操作员在界面上无法按实际作业海区调整，更换海区必须改代码重新编译。

### 1.3 为什么这是"项目真正需要"的信息

均衡算法的目标是在给定的载荷（人员、压载铅、各水舱充装量）下求解如何调整水舱和压载铅，使纵倾力矩归零。密度的两条进入路径都是**量的换算**：

- 质量 ↔ 体积：`V = m/ρ`（排多少升水才能抵消多少千克的人员重量）
- 体积 ↔ 力矩：`M = V·ρ·L`（某个水舱排空会带来多大力矩变化）

这两条路径决定了密度不是一个装饰性的参数，它直接参与决策。而在水下救援模式下，300 m 处的密度比表层重约 0.46%，如果算法用一个表层值去算 300 m 的排水量，就是系统性的换算偏差。

**但"参与决策"不等于"改变决策"**——这正是后面敏感性实验要回答的问题，也是本次实验最有价值的发现来源。

## 2 获取方案的设计

### 2.1 设计约束

| 约束 | 说明 |
| --- | --- |
| 不可出海实测 | 实验周期内不可能组织现场 CTD 观测 |
| 必须可复现 | 任何人按文档重跑应得到相同结果 |
| 必须有出处 | 数据要能追溯到权威机构与具体版本 |
| 必须有不确定度 | 否则无法判断结论的置信程度 |
| 必须覆盖中国近海 | 项目作业海域为渤海/黄海/东海/南海 |
| 必须覆盖深度 | 水下救援模式涉及 0–300 m |
| 规模最小 | 一天内可完成，不做全海域全月份全深度 |

### 2.2 方案选择

| 候选方案 | 结论 | 理由 |
| --- | --- | --- |
| 现场 CTD 实测 | ✗ | 不可行，成本与周期不匹配 |
| 卫星遥感海表密度反演 | ✗ | 只覆盖表层（约 0–10 m），无法支撑 300 m 的救援工况 |
| **WOA23 全球海洋气候态数据集** | **✓ 采用** | NOAA 官方发布，1° 网格，含温度/盐度及其标准差，覆盖 0–300 m 全部标准层，免费公开，有版本号可追溯 |
| 区域再分析产品（如 CMEMS） | △ 备选 | 分辨率更高，但数据量大、下载门槛高，与"最小可行"原则不符 |

### 2.3 采用的技术路线

```
NOAA WOA23 气候态（1991–2020）
  温度 t（an/sd/dd）  ─┐
  盐度 s（an/sd/dd）  ─┤ 4 个海区 × 4 个月份 × 29 个深度层
                       │
                       ▼
         温标换算 ITS-90 → IPTS-68（T68 = 1.00024·T90）
                       │
                       ▼
         压力换算 p = press(深度, 纬度)
                       │
                       ▼
         EOS-80 状态方程 ρ = ρ(S, T68, p)     ← UNESCO 1983
                       │
                       ▼
         不确定度传播 u(ρ) = √[(∂ρ/∂T·u_T)² + (∂ρ/∂S·u_S)²]
                       │
                       ▼
              质量控制（6 类判据）
                       │
                       ▼
        结构化数据集 + 敏感性实验
```

**为什么用 EOS-80 而不是更现代的 TEOS-10？** EOS-80 是本项目量级（浅海、0–300 m、工程计算）下的成熟标准，公式简单、依赖库通用、便于与外部核对。作为对照，本实验对 EOS-80 的实现做了标准值校验（见 §4.1）。TEOS-10 的差别在本项目量级下远小于密度本身的时空跨度，留作后续改进项。

**关键实现细节：温标换算。** WOA23 的温度为 ITS-90 温标，而 EOS-80 要求 IPTS-68，两者差 `T68 = 1.00024·T90`。忽略这一步会引入约 0.006 kg/m³ 的系统偏差——虽然不大，但属于**方法性错误**而非数据噪声，必须处理。这一条是本实验在设计阶段就识别出来的陷阱，也是最容易被忽略的一步。

### 2.4 取样设计（最小可行的具体含义）

| 维度 | 取样 | 说明 |
| --- | --- | --- |
| 海区 | 4 个格点 | 渤海中部(38.5N,119.5E)、黄海中部(35.5N,123.5E)、东海陆架(28.5N,125.5E)、南海北部(18.5N,114.5E) |
| 月份 | 4 个 | 1/4/7/10 月，代表冬/春/夏/秋 |
| 深度 | 29 层 | WOA23 标准层 0–300 m 全部（0,5,10,15,20,25,…,300） |
| 变量 | 6 个 | 温度与盐度的气候态平均 an、标准差 sd、观测支撑 dd |
| 合计 | 464 条 | 4×4×29 − 因缺测略少，实际生成 464 条（含缺测标记） |

**取样数的取舍理由**：4 个海区足以覆盖项目的作业海域差异；4 个月份足以刻画季节信号的一阶特征（冬夏对比最强，春秋为过渡）；29 个标准层是 WOA23 自带的深度网格，不做插值以免引入额外假设。全海域全月份（12 个月 × 1° 全网格）会得到数十万条记录，对本次"验证方法可行性"的目的而言是过度的。

## 3 实际执行过程

全部脚本位于 `experiments/seawater_density/scripts/`，按序号依次执行。

### 3.1 步骤 1：下载原始数据

**脚本**：`01_fetch_woa23.py`

**数据源**：`https://www.ncei.noaa.gov/data/oceans/woa/WOA23/DATA/`

**下载内容**：`temperature` / `salinity` 两个变量目录 × 4 个月份 × 3 个统计量（an/sd/dd）= **24 个 CSV(.gz) 文件**，合计 **55 MB**。

文件命名规则示例：`woa23_decav91C0_t01an01.csv.gz` = 温度(t) 1月(01) 气候态平均(an) 1° 网格(01)。

**工程处理**：脚本实现了带 HTTP Range 断点续传的下载，失败自动重试 3 次，已存在且非空的文件跳过。实际执行过程中出现了数次网络中断，续传机制使得重跑不必从头开始。

```bash
python scripts/01_fetch_woa23.py
# 输出：完成：成功 24，失败 0
```

### 3.2 步骤 2：构建密度数据集

**脚本**：`02_build_density_table.py`

执行内容：解析 24 个原始文件 → 在 4 个格点上提取 29 个标准层的温盐 → 温标换算 → 压力换算 → EOS-80 复算密度 → 不确定度传播 → 6 类质量控制 → 输出结构化数据。

**执行中遇到并解决的一个真实问题：WOA23 的 CSV 产品会省略行尾的缺测值。**

这导致数据行具有**变长的字段数**（3–59 个不等），用常规的定长表格解析（如 `pandas.read_csv` 直接读）会报 `Expected 41 fields in line 5, saw 42`。解决办法是改写为手工解析：读取表头得到该文件的深度列表，逐行按该列表索引取值，**索引超出该行长度即判定为缺测**。

这个问题本身就是一个数据质量发现：**"文件里有这一行"不等于"这一层有数据"**。如果按常规解析并通过填充默认值处理，会把缺测悄悄变成 0 °C 或 0 PSU 的假数据——这类静默错误在工程数据里危害极大。

```bash
python scripts/02_build_density_table.py
# 输出：464 条记录，其中缺测 188，QC 通过 276
```

### 3.3 步骤 3：算法复刻与敏感性实验

**脚本**：`03_sensitivity_scan.py`

执行内容分两部分：

**(a) 算法复刻与校验。** 用 Python 逐行复刻 `solve_departure()` 与 `solve_rescue()` 的决策逻辑（含压载铅离散枚举、铁块横向移动、四个救生舱组的排水顺序、尾组与指挥舱的启用条件），然后用**解析判据**验证复刻是否忠实（见 §4.5）。这一步是必需的：复刻一旦失真，后面所有敏感性数字都没有意义。

**(b) 四个敏感性实验**：

| 实验 | 设计 | 目的 |
| --- | --- | --- |
| 实验一 | ρ 在真实区间 [1.0203, 1.0276] 取 200 个点，对同一批 1500 个工况重跑 | 看翻转率随 ρ 的**单调趋势**与最大值 |
| 实验二 | 276 条真实密度**逐条代入**，共 414000 次比对 | 给出真实数据下的**加权翻转率**（按真实分布，而非均匀扫描） |
| 实验三 | 水面模式 `solve_departure()`，4 种水舱状态 | 检查密度在水面模式是否真正参与运算 |
| 实验四 | 把 Δρ 折算成力矩与排水读数 | 给出**工程量纲**的解释 |

**工况样本集的构造**（1500 个，随机种子 `20261014` 保证可复现）：水舱充装比例 ∈ {1.0, 0.75, 0.5, 0.25, 0.0}，指挥舱充装比例 ∈ {0, 0.25, 0.5, 0.75, 1}，被救人员 1–6 人、体重 50–100 kg、随机落座于 1–18 号座位，压载铅配置在物理可行范围内随机。

### 4.3 数据覆盖的真实边界（本次实验的重要发现）

**各海区实际可用的深度并非"300 m"，而是受实际水深限制：**

| 海区 | 最大可用深度 | 观测支撑 dd | 说明 |
| --- | --- | --- | --- |
| 渤海中部 | **20 m** | 文件中**整行缺失** | 平均水深约 18 m，25 m 以深无水体 |
| 黄海中部 | **60 m** | 2–6 | 水深约 50–80 m |
| 东海陆架 | **125 m** | 10–27 | 陆架水深约 100 m |
| 南海北部 | **300 m** | 1–7 | 陆坡深水区，0–300 m 全覆盖 |

**这本身就是"缺失信息"的第二层含义**：项目的救援模式按 300 m 设计，但渤海、黄海、东海三个近海海区**根本提供不了对应深度的观测数据**——不是数据没拿到，而是那里没有那么深的水。只有南海北部具备完整剖面。

更进一步，即便在能取到数值的格点上，观测支撑也很薄：黄海中部 dd 仅 2–6，南海北部 1–7，渤海格点在 dd 产品中无记录。作为对照，WOA23 该字段在全球范围内的取值可达 **728**（本实验实测）。也就是说中国近海这几个格点的气候态是由个位数到二十几次观测撑起来的。

> **说明**：WOA23 官方对 `dd` 的定义是 "Data distribution"，本实验**未假定**它就是观测次数，只把它当作"观测支撑强弱"的相对指标使用，并据此给出**不否决记录**的覆盖度警告。

### 4.4 判据清单

| 类型 | 判据 | 是否否决记录 | 命中 |
| --- | --- | --- | --- |
| 缺测 | 该深度无温盐值 | **是**（该层无数据） | 188 项 |
| 量程 | T∈[-3,40] °C，S∈[0,42]，ρ∈[1000,1045] kg/m³ | 是 | 0 项 |
| 层化 | 同海区同月份，密度随深度不得减小超过 0.01 kg/m³ | 是 | 0 项 |
| 覆盖度 | dd 缺失或 < 10 | 否，仅提示 | 1 项 |
| **算法校验** | EOS-80 标准值偏差 < 0.01 kg/m³ | — | 通过 |
| **合理性** | 见 §4.6 | — | 0 项异常 |

**关于"缺测"的定性**：188 项缺测绝大多数是**合理的物理缺测**（水深不足，那里本来就没有水），而非观测缺失或数据错误。这一点必须在报告中区分清楚——把它当作"数据质量问题"去修补（例如向深水层外推）反而会制造出虚假数据。**正确的处理是承认覆盖边界，并把这个边界传递给下游使用者。**

### 4.5 复刻算法的解析校验（保证后续数字可信）

复刻是否忠实不能靠"看起来对"。本实验用**解析判据**校验：

**排水分支的判据**：`solve_rescue()` 的排水分支只由所需排水量 `need_L = W/ρ` 与一组固定容量阈值的比较决定。因此当 ρ 由 1.020 变到 1.0276 时，**发生翻转的载荷 W 必须落在 `[T·ρ₁, T·ρ₂]` 这个窗口内**（T 为某个阈值）。

**压铅的判据**：压铅取的是"使总力矩 ≥ 0 的最小 delta"，等价于在 delta 的离散格点集合中取 ≥ `need` 的最小格点。need 由 need₁ 漂移到 need₂ 时，选择改变**当且仅当有格点落在 `[need₁, need₂)` 内**。

| 校验项 | 结果 |
| --- | --- |
| 细网格样本数（3 种舱态 × 901 个载荷 × 3 种乘员排布） | 8109 |
| 排水分支翻转处数 | 189 |
| 其中落在解析阈值窗口内 | **189 / 189** |
| 压铅翻转处数 | 131 |
| — 其中与排水分支同步变化（不计入判据） | 19 |
| — 其余符合格点区间判据 | **112 / 112** |

**全部翻转点都能被解析判据解释，命中率 100%**，说明复刻与 `Main.qml` 行为一致，后续翻转率数字可信。

**过程中修正的两个错误（记录备查）**：

1. 第一版校验的阈值集合写漏了（只写了 570/712.5/855/997.5，漏了 142.5/285/427.5/600），命中率只有 15%。补齐后才发现 `if (remaining_needed_L <= 0.01) break;` 使每组启用阈值带 **+0.01 L 容差**，而分支切换与指挥舱启用是**精确比较**。
2. 压铅判据最初写成"need 距下方最近格点的距离"，这是错误的量，命中率 83%。改为"区间内是否存在格点"后达到 100%。

> 这两处修正说明：**敏感性分析的数字必须能被独立判据解释，否则可能只是复刻 bug 的产物。**

### 4.6 合理性检查

| 判据 | 设计理由 | 结果 |
| --- | --- | --- |
| 季节性：表层密度 1月 > 7月 | 北半球冬高夏低 | 全部通过 |
| 空间梯度：盐度应为 渤海 < 黄海 < 外海 | 近岸受河流淡水影响 | 全部通过 |
| **共** | | **0 项异常** |

**两条被主动放弃的判据（避免用错误先验制造假异常）**：

- **"10月 > 4月"不成立**：秋季表层受夏季增温余热与长江冲淡水影响，可以比春季更轻。这是真实海洋特征，不是数据错误。
- **"密度空间排序"不成立**：冬季渤海约 4 °C 的水比南海约 24 °C 的表层水**更重**。密度的空间排序被温度主导，不能作为判据；判据必须改用**盐度**。

> 这一条是本次实验在方法论上最值得记录的经验：**"发现 18 项异常"最终被证明是我自己的先验知识错误**。质量控制的第一步是先检查判据本身是否成立。

### 4.7 不确定度传播

按 `u(ρ) = √[(∂ρ/∂T·u_T)² + (∂ρ/∂S·u_S)²]` 传播，偏导数用中心差分（步长 0.01），`u_T`、`u_S` 取 WOA23 的 sd 字段：

| 统计量 | 值 |
| --- | --- |
| 不确定度中位数 | **0.1893 kg/m³** |
| 不确定度 90 分位 | 0.4314 kg/m³ |
| 不确定度最大值 | 1.0654 kg/m³ |

若按 `sd/√dd` 折算为标准误，中位数为 0.0765 kg/m³（该折算依赖 dd 的语义，仅作参考）。

**一个重要的方法学结论**：sd 反映的是网格内**变率**（年际＋空间），把它当作不确定度是**保守上界**。但无论取哪一种，不确定度（0.19–1.07 kg/m³）都**远小于密度取值本身的时空跨度（7.6 kg/m³）**。因此后续敏感性分析以**密度取值跨度**而非统计不确定度作为自变量——因为对算法而言，"用了错的海区/季节"比"这个格点本身测不准"影响大得多。

## 6 敏感性实验结果

> 本节所有数字均基于经 §4.5 解析校验（命中率 100%）的算法复刻。

### 6.1 实验一：密度扫描（200 个 ρ 取值 × 1500 工况）

以程序常数 ρ=1.020 为基准，让 ρ 在真实区间上取值：

| 密度(kg/L) | 排水分支翻转 | 压铅翻转 | 任一变化 | 最大力矩差(kg·m) |
| --- | --- | --- | --- | --- |
| 1.0203（真实下界） | 0 (0.0%) | 1 (0.1%) | 1 (0.1%) | 0.7 |
| 1.0215 | 1 (0.1%) | 6 (0.4%) | 6 (0.4%) | 1685.9 |
| 1.0238 | 2 (0.1%) | 14 (0.9%) | 14 (0.9%) | 1686.6 |
| 1.0250 | 7 (0.5%) | 18 (1.2%) | 23 (1.5%) | 1686.9 |
| 1.0262 | 9 (0.6%) | 19 (1.3%) | 26 (1.7%) | 1687.3 |
| **1.0276（真实上界）** | 10 (0.7%) | 20 (1.3%) | **28 (1.9%)** | **1687.7** |

- 翻转率随 ρ **单调上升**：ρ 越大，所需排水量越小，越容易跨过容量阈值。
- 在真实密度区间的上界附近，**最大翻转率 1.9%**。

### 6.2 实验二：真实密度逐条代入（276 条 × 1500 工况 = 414000 次比对）

实验一假设 ρ 在区间上均匀分布，但真实密度**并非均匀分布**。实验二直接按真实记录逐条代入：

| 决策层面 | 翻转次数 | 占比 |
| --- | --- | --- |
| 排水分支（用哪些水舱） | 1235 | 0.298% |
| 压载铅建议（位置/块数） | 3956 | 0.956% |
| **任一变化** | **4693** | **1.134%** |

**按海区**：

| 海区 | 任一变化 | 记录数 |
| --- | --- | --- |
| 渤海中部 | 0.95% | 20 |
| 黄海中部 | 1.31% | 52 |
| 东海陆架 | 1.16% | 88 |
| 南海北部 | 1.06% | 116 |

**按月份**：

| 月份 | 任一变化 |
| --- | --- |
| 1月 | 1.34% |
| 4月 | 1.29% |
| 7月 | 0.94% |
| 10月 | 0.96% |

**按深度**：翻转率随深度**单调上升**，0 m 为 0.75%，100 m 为 1.48%，300 m 为 **1.87%**。

> **深度趋势的物理含义**：深水密度更大 → 所需排水量更小 → 更容易跨过水舱容量阈值 → 排水分支更容易翻转。这与 §4.3 发现的"深水数据覆盖不足"叠加在一起，构成一个**风险集中区**：恰恰是数据最稀缺、翻转率最高的深度段。

### 6.3 实验三：水面模式——密度是死代码

| 水舱状态 | 压铅翻转 | 最大力矩差(kg·m) |
| --- | --- | --- |
| **全满舱（救生舱+指挥舱，程序默认）** | 0/1500 | **0.000** |
| 救生舱满、指挥舱空 | 0/1500 | 9.732 |
| 救生舱半舱、指挥舱空 | 0/1500 | 4.786 |
| 救生舱 1/4 舱、指挥舱空 | 0/1500 | 2.313 |

**这是本次实验最直接的一个结构性发现。**

程序默认水舱是**满舱**（救生舱 4×142.5 L，指挥舱 `tCmd1="215"` + `tCmd2="215"` = 430 L，见 `Main.qml:461-462`）。此时每一舱的 `missing = 容量 − 当前 = 0`，`solve_departure()` 里所有含密度的项都被 `if (missing > 0.01)` 挡在外面——**密度根本不参与任何运算，换什么密度结果都逐位相同**。

只有水舱不满时密度才进入计算。即便在"救生舱满、指挥舱空"这一情形下，9.7 kg·m 的力矩差**完全来自指挥舱**（430 L × Δρ × 2.969 m），与救生舱组的充装状态无关；而这个量级仍然**小于移动最小一块压载铅的台阶 53.2 kg·m**。

### 6.4 实验四：误差的工程量纲

ρ 由 1.020 变到真实上界 1.0276（Δρ = 7.62 kg/m³，相对 0.75%）时，各水舱满舱对应的力矩变化：

| 物理量 | 力矩变化(kg·m) |
| --- | --- |
| 尾组全排空 600 L | +17.55 |
| 救生舱组 1 满舱 142.5 L | +1.35 |
| 救生舱组 2 满舱 142.5 L | +2.10 |
| 救生舱组 3 满舱 142.5 L | +2.85 |
| 救生舱组 4 满舱 142.5 L | +3.60 |
| 指挥舱满舱 430 L | −9.73 |

**压载铅移动一块的力矩台阶：53.2 / 55.2 / 108.4 kg·m**（压载铅 20 kg，站位间距不等；另有 618 kg 压载铁用于横向调整）。

排水读数的换算偏差（相对偏差恒等于 ρ 的相对偏差 **0.75%**，与载荷大小无关）：

| 获救人员总重 | 排水读数@1.020 | 排水读数@真实 | 差 |
| --- | --- | --- | --- |
| 300 kg | 294.12 L | 291.94 L | 2.18 L |
| 600 kg | 588.24 L | 583.87 L | 4.36 L |
| 900 kg | 882.35 L | 875.81 L | 6.55 L |

### 6.5 结论：误差小而集中

把所有结果放在一起，得到一个清晰的二分结构：

| 情形 | 力矩偏差量级 | 相对压载铅最小台阶（53.2 kg·m） | 占比 |
| --- | --- | --- | --- |
| **不发生分支翻转**（绝大多数） | ≤ **17.6 kg·m** | **小于一块铅** | ~98.9% |
| **发生排水分支翻转** | **1687.7 kg·m** | 约 **32 块铅** | ~1.1% |

两者相差**两个数量级**。

三个层次结论：

1. **水面模式**：密度是死代码。默认满舱时 ρ 完全不进入运算，改成真实密度不会改变任何输出。
2. **水下救援模式**：密度通过 `W/ρ`（所需排水量）和 `V·ρ·L`（力矩损失）两条路径进入，但**绝大多数工况下结论不变**（1.13%）。
3. **但变化的那一小部分是危险的**：排水分支一旦翻转，力矩损失突变 **1687.7 kg·m ≈ 32 块压载铅**的调节能力——这是量级完全不同的决策差异（实测边界工况：力矩损失由 2348.2 变为 660.5 kg·m）。

> **注**：本实验只检验**决策是否改变**，不检验决策的**物理正确性**。算法本身的合理性不在本次实验范围内。

## 7 三个问题

### 7.1 缺的是什么信息？

**表面答案**：缺真实海水密度，程序用的是硬编码的 1.020 kg/L。

**更准确的答案**：缺的是**密度的时空结构、深度结构，以及它的可信度信息**。具体拆成四条：

1. **空间维度**——同月份不同海区表层密度相差 2.2 kg/m³（1 月：黄海中部 1025.10 vs 南海北部 1022.93）。
2. **时间维度**——同一海区季节差可达 4.4 kg/m³（黄海中部表层 1 月 1025.10 vs 7 月 1020.70）。
3. **深度维度**——南海北部 0 m 到 300 m 相差 4.7 kg/m³，且深层季节性几乎消失。
4. **可信度维度**——没有任何不确定度与来源信息，无法判断一个数值有多可靠。

还有一条**关键补充发现**，是实验前的方案设计里没有预料到的：

5. **数据覆盖本身的缺失**——项目按 300 m 深度设计救援模式，但渤海（可用至 20 m）、黄海（60 m）、东海（125 m）三个海区**在物理上就没有那么深的水**，WOA23 也无从提供。**"这个信息不存在"不是因为没去找，而是因为它本来就不存在。** 这是本次实验最符合"从信息缺失到可用数据"主题的发现。

### 7.2 如何可靠地获得？

**方法**：用权威公开的气候态产品（NOAA WOA23 decav91C0，1991–2020）+ 国际标准状态方程（EOS-80/UNESCO 1983）复算，而不是现场实测。

**可靠的四个支点**：

| 支点 | 具体做法 |
| --- | --- |
| **来源可信** | NOAA 官方发布，带版本号与统计期，可追溯可复核 |
| **算法可信** | EOS-80 标准校验点比对通过（1025.9720 vs 1025.973） |
| **处理可信** | 温标换算（ITS-90→IPTS-68）、压力换算（含纬度）、不确定度传播都是显式的、可审查的步骤 |
| **质控可信** | 6 类判据 + 合理性检查 + 不确定度标注；判据本身经过反思修正（见 §4.6） |

**可靠性的三个"不"**：

1. **不假装覆盖**：缺测就标缺测，不向深水层外推填充。渤海 25 m 以深就是没有数据，这个事实必须如实传递。
2. **不隐藏薄弱**：观测支撑只有 2–7 次记录的格点，用覆盖度警告标出来，而不是当作和 728 次记录一样可信。
3. **不用错误先验制造假异常**：发现"18 项异常"时先检查判据本身，最终确认是判据错了（秋季可以比春季轻；冬季渤海比南海表层重），而不是数据错了。

**唯一性说明**：本方法的可靠性建立在"气候态 + 标准方程"上，它给出的是**该海区该月份该深度的长期平均**，不是作业当时的实时值。对于实时性要求，需要现场 CTD 或实时预报产品——这超出本次实验范围，但边界必须在报告中写明。

### 7.3 哪个判断或设计因此改变了？

这是本次实验最重要的部分。**改变的不是一个参数，而是三个判断。**

#### 判断一：从"换真实密度会显著改进决策" → "只有 1.13% 的决策会变"

实验前的直觉是：密度直接影响排水量与力矩换算，用错的密度应该会带来普遍的决策偏差。实测结果是 **1.13%**（压铅 0.96%，排水分支 0.30%）。

这个数字本身就是一个设计依据：**如果只是把常数换成真实值，绝大多数情况下输出完全一样**——投入产出比需要用"改变的那 1.13% 值不值得"来衡量。

#### 判断二：从"水面模式也受益" → "水面模式里密度是死代码"

原以为两个模式都会受益。实验发现 `solve_departure()` 的密度项全部被 `if (missing > 0.01)` 保护，而程序的默认水舱状态恰恰是满舱——**密度在水面模式下根本不参与运算**。

这个发现改变了对改造范围的估计：如果按"两个模式都要改"来规划工作量，会有一半是无效功。

#### 判断三（核心）：从"误差小 → 不重要" → "误差小而集中 → 必须做鲁棒化设计"

这是本次实验最有价值的判断改变。

原始思路是：`|Δρ| ≤ 0.75%`，折算到力矩最大 17.6 kg·m，**小于移动一块压载铅（53.2 kg·m）**，所以"影响可以忽略"。

但敏感性实验揭示了这个推理的漏洞：**平均/最大的连续偏差小，不代表决策不会离散地跳变。** 算法的排水分支是**阈值判断**（`need_L` 与一组容量阈值比较），阈值判断的误差传播不是连续的，而是**在临界点上产生离散跳变**——一旦跨过，力矩损失突变 **1687.7 kg·m ≈ 32 块压载铅**。

**判断因此改变为**：

> 密度参数化的价值不在于"把 1.020 换成更准的数"，而在于**识别出那些处在阈值临界点附近的工况，并在那里做保守化处理**。真正需要的设计不是"更准的密度"，而是"对密度不确定性的鲁棒性"。

**由此产生的设计方向（后续工作，本次实验未实现）**：

| 方向 | 内容 |
| --- | --- |
| 1 | ρ 从编译期常量改为**带来源的运行时参数**（海区 + 月份 + 深度），界面可按实际作业海域设定 |
| 2 | 对临界工况做**保守化**：当 `need_L` 落在容量阈值 ±Δ 窗口内时，给出警示或选择保守分支，而不是给出一个"看起来精确"的单一答案 |
| 3 | 把**密度的不确定度**作为算法输出的一部分，让操作员看到"这个方案对密度有多敏感" |
| 4 | 对渤海/黄海/东海深水工况**明确标注数据不覆盖**，不给出伪装成精确解的答案 |

**第 2 条是本次实验最实质的方法论产出**：它把一个"数据获取任务"转化成了一个"算法鲁棒性设计任务"。数据本身不能解决问题——**只有理解了数据如何进入决策，才知道该改什么**。

## 8 对项目后续推进的影响

### 8.1 已经确定的事实

| 事实 | 依据 |
| --- | --- |
| 水面模式改密度**没有任何效果**（默认满舱时） | 实验三：力矩差 0.000 kg·m |
| 水下救援模式**只有 1.13% 的决策会变** | 实验二：414000 次比对 |
| 但分支翻转的代价是 **32 块压载铅** | 实验一：1687.7 kg·m 断崖 |
| 深水（>150 m）**翻转率最高**（1.87%）**且数据覆盖最差** | 实验二按深度分组 + §4.3 覆盖分析 |
| 硬编码的 1.020 是**系统性偏轻值**（实测 0/276 低于它） | §5.2 |

### 8.2 建议的推进路径

| 优先级 | 事项 | 理由 |
| --- | --- | --- |
| **高** | 在 `solve_rescue()` 中识别并标注**临界工况**（`need_L` 靠近容量阈值时给出警示） | 这是 1.13% 里真正危险的部分，改动小、收益直接 |
| **高** | 密度改为**运行时参数**，界面提供海区/季节选择，默认值仍为 1.020 以保持向后兼容 | 不改算法逻辑即可让操作员按实际情况设定 |
| 中 | 把 `density_lookup.json` 接入程序，实现"海区+月份+深度 → 密度"查表 | 数据结构已就绪，接入成本低 |
| 中 | 算法输出中附带**密度敏感度提示** | 让操作员知道方案对密度的依赖程度 |
| 低 | 引入 TEOS-10 替换 EOS-80 | 本项目量级下差异远小于时空跨度，收益有限 |
| 低 | 扩大取样（12 个月份、更细网格、更多海区） | 现有 4×4 取样已足以支撑本次结论 |

### 8.3 需要外部条件才能推进的部分

如果要把密度从"气候态"提升到"实时值"，需要以下任一条件，均超出本次实验范围：

- 现场 CTD 观测（作业前实测温盐剖面）
- 接入实时海洋预报产品（如 CMEMS 区域再分析/预报）
- 作业海域的历史实测数据积累

**在没有这些条件的情况下，气候态数据的正确用法是"给出典型值 + 标注不确定度 + 标出覆盖边界"，而不是假装它是实时精确值。** 这是本次实验希望确立的使用原则。

## 9 局限性与下一步

### 9.1 本次实验的局限（必须明示）

| 局限 | 说明 | 影响范围 |
| --- | --- | --- |
| **气候态 ≠ 实时值** | WOA23 是 1991–2020 的长期平均，不含当天的中尺度涡、锋面、淡水团 | 密度取值的绝对正确性 |
| **1° 网格分辨率不足** | 中国近海近岸梯度大，1°（约 100 km）无法分辨近岸锋面 | 近岸工况 |
| **只有 4 个月份** | 1/4/7/10 月代表四季，未覆盖逐月变化 | 过渡季节 |
| **dd 语义未确认** | 官方定义为 "Data distribution"，本实验未假定其为观测次数 | 覆盖度警告的定量解释 |
| **只检验决策是否改变** | 不检验算法决策本身的物理正确性 | 结论的适用范围 |
| **复刻而非直接调用 QML** | Python 复刻经解析判据 100% 校验，但仍是复刻 | 理论风险已通过校验最小化 |
| **工况集为合成样本** | 1500 个随机工况，非真实作业记录 | 翻转率的代表性 |

### 9.2 下一步

1. **短期**：把 §8.2 的"高优先级"两项做成具体改造方案（临界工况警示 + 运行时密度参数）。
2. **中期**：接入 `density_lookup.json`，并在界面上给出"当前方案的密度敏感度"。
3. **长期**：评估接入实时海洋预报产品的可行性与成本，或建立作业海域的实测数据积累机制。

## 10 结语

本次实验的起点是一个很朴素的问题：程序把海水密度写死成 1.020，能不能换成真实的？

实验做完之后，答案变成了三句话：

1. **能拿到**——用权威气候态数据 + 标准状态方程，一天内可以构建出 276 条带质控与不确定度的密度记录，算法校验通过。
2. **但影响比想象的小**——只有 1.13% 的决策会改变，水面模式下密度甚至完全不参与运算。
3. **然而小影响集中在大风险上**——分支翻转的力矩断崖是 32 块压载铅，而这恰恰发生在数据覆盖最差的深水区。

**从"缺一个数"到"知道这个数在算法里怎么起作用"，这才是本次实验真正的产出。** 数据获取的价值不在于拿到数据本身，而在于它让你看清了系统的哪个部分真正依赖于它。
